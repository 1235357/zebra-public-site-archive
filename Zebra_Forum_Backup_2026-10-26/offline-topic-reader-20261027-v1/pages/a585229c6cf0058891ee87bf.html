                  So we have ZD500R UHF RFID printers. Our labels are roughly 2 inches wide and 1 inch tall. I have an odd situation, in terms of trying to remotely troubleshoot an EPC encoding issue. Doesn't happen often, but when it does it's difficult to narrow down as to the root cause.I have a small C# app that translates a user request to ZPL to send to the ZD500R. The requests are sent serially, for one label at a time. The unique ID for the item associated with the label is both printed on the label and encoded as the EPC. This unique ID is handled as a string, not an integer when being translated to send as a ZPL print job.We run into sporadic cases where a label prints with the correct unique ID visible. But the previous print job's EPC value is encoded on it. Before I send the print job, I send a command to clear the printer. And after the print job has completed, I send a command to flush the print buffer. A few cases where this happened I see that the print jobs are spaced out 30 seconds to a minute apart. So it's not like some buffer overrun due to rapid fire. Would this just seem to be an RFID calibration issue that could cause this? As far as I know, there wasn't a failed print job leading to VOID printing across a label or anything. This happens maybe 5% of the time. The rest of the time it's fine.I'll attach an example pic, where the unique ID printed on the label is 00062755. But the EPC value that was encoded was from the previous print job, 00062754.And below is an example of the ZPL being sent to the ZD500R for a print job. The 00001234 is the unique ID that's printed on the label and EPC encoded. ^XA^MMT^PR0,12,12~TA000^LH0,0~SD29^PW812^RFW,A^FD00001234^FS^FO250,25^BQN,2,2,M,^FDMA,01000000IT1234512100001234^FS^A@N,25^FO325,50^FD$100^FS^A@N,15^FO250,90^FDTest item^FS^A@N,15^FO250,104^FD^FS^A@N,20^FO250,10^FDIT12345 : 00001234^FS^XZ
