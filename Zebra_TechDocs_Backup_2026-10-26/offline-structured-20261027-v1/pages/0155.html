Identity Guardian 3.3

Overview

Identity Guardian provides secure, frictionless device access while safeguarding user data. To accommodate diverse operational workflows, the application offers two primary device deployment architectures:

  • Shared Device: Designed for multi-user device pools, utilizing encrypted barcodes or NFC cards followed by optional secondary verification (facial biometrics, passcode, or SSO). Alternatively, configure Guardian Safe with MPIN to secure credentials and personalized settings on Shared Devices using a Master Personal Identification Number (MPIN).
  • Personally Assigned Device: Designed for dedicated, single-user devices, streamlining access via facial biometrics, SSO or a local passcode with secured user privacy.

Users must enroll in the system prior to authenticating on a device. Integration with identity providers (IdPs) enables single sign-on (SSO) to streamline application access with a single login.

Deployment and configuration are managed utilizing one of the following platforms:

  • Zebra DNA Cloud: Provides centralized application management via My Apps > Zebra Collection along with an administrative dashboard for operational insights and device usage tracking.
  • Enterprise Mobility Management (EMM) system: Enables administrators to deploy the application and establish usage policies, device controls, and restrictions via Managed Configurations.

Secure NFC extends Identity Guardian authentication by enabling encrypted credential storage on contactless smart cards. The architecture pairs Identity Guardian for policy-driven card reading and user sign-in with zCreator for secure card provisioning and credential encryption, delivering enterprise-grade badge authentication without disrupting existing building access infrastructure.

Secure NFC

Secure NFC provides hardware-level, encrypted authentication for workers using contactless smart cards. Operating alongside the zCreator companion app, Secure NFC enables organization to migrate from unencrypted card storage to encrypted storage with zero-downtime key rotation and multi-application card coexistence with existing enterprise access control systems.

Identity Guardian supports two card data storage architectures:

  1. Secure Layer (Recommended): Encrypts user credentials using cryptographic key sets. Supports Append Mode, allowing Identity Guardian to write credential data without corrupting existing card applications (such as building access control).
  2. Standard NDEF (Legacy): Uses the standard open NFC Data Exchange Format. Does not support encryption or card coexistence; writing in NDEF format overwrites all existing data on the card.

To deploy using an EMM, refer to Shared Devices and configure NFC Configurations for Identity Guardian and zCreator within Managed Configurations.

Read/Write Execution Logic

Operational behavior across Identity Guardian and zCreator depends on the selected NFC Data Storage mode and the other configured Managed Configuration policies.

  • Read Operations (Identity Guardian): Identity Guardian utilizes an adaptive read flow that automatically falls back between formats. This enables simultaneous support for legacy unencrypted cards and modern encrypted cards across the same device fleet without administrative intervention. If both reads fail, it tries the Default Factory Key.
    • When set to "Standard NDEF": Identity Guardian attempts to read unencrypted NDEF records first. If no valid NDEF data is detected, it falls back to read Secure Layer data.
    • When set to "Secure Layer": Identity Guardian evaluates encrypted sectors using the configured key hierarchy first. If no secure record is found, it automatically falls back to read legacy NDEF data.
  • Write Operations (zCreator): The zCreator enrollment application consistently provisions new credentials using the configured Primary Write Key. Data handling varies by storage mode:
    • Standard NDEF: Data is written to the unencrypted NDEF public message area. NDEF does not support data appending; performing a write operation overwrites existing card data.
    • Secure Layer (Encrypted): Credentials are encrypted and written to dedicated secure sectors. When User Data Operation is set to Append, zCreator allocates available secure sectors to write Identity Guardian credentials without altering existing third-party card data (such as access control systems).

Application Identifier (AID)

The Application Identifier (AID) is a unique 3-character alphanumeric string that identifies the specific memory sector reserved for Identity Guardian on the card.

  • Matching Requirement: The AID configured in the Identity Guardian read policy must match the AID configured in the zCreator write policy.
  • Function: During a card tap, Identity Guardian queries the card directory for this specific AID to locate and decrypt user credentials rapidly.

Security Keys

When deploying Secure NFC, administrators must define security keys in EMM Managed Configurations. If key fields are left blank, the applications automatically fall back to proprietary factory default keys.

Custom encryption keys deployed through EMM must comply with strict format requirements. For details, refer to the respective Identity Guardian and zCreator sections for NFC Configuration.

Security best practices dictate periodic key rotation. Identity Guardian uses a dual-key (Primary and Secondary) architecture to ensure seamless key transitions across active card fleets without operational disruption:

  • Write Logic: zCreator always writes new credentials using the configured Primary Write Key.
  • Read Logic: Identity Guardian evaluates keys in sequence: Primary Read Key ➔ Secondary Read Key ➔ Factory Default Key.

Key Rotation Procedure:

  1. In the EMM console, copy the existing active production key into the Secondary Key fields (Secondary Read / Secondary Write) for both Identity Guardian and zCreator.
  2. Enter the newly generated key into the Primary Key fields (Primary Read / Primary Write).
  3. Deploy the updated policy profiles.
  4. Active cardholders continue authenticating via the Secondary Key fallback until their cards are reprovisioned with the new Primary Key during regular enrollment cycles.

Best Practices

  • Card Stability During Write: Operators must hold the card stationary against the mobile computer's NFC antenna until the on-screen confirmation displays. Premature removal interrupts writing and can lock the card sector.
  • Card Overwrite Protection: To prevent accidentally overwriting an active employee badge, ensure the Allow Different User Overwrite parameter is set to false in the zCreator policy.
  • Downgrade Sanitization: When migrating cards from Secure Layer back to legacy NDEF, always execute a Wipe card and write operation to prevent orphaned encrypted blocks from lingering in card memory.

SSO Integration

Identity Guardian integrates with identity providers (IdPs) to simplify authentication. Users log in only once, leveraging Single sign-on (SSO) to streamline the process. This single login grants access to multiple applications, eliminating the need to manage separate credentials for each app.

Important: The following sections provide general integration guidance. Actual interfaces and step-by-step processes may vary due to updates in third-party IdP software.
  • Microsoft Entra ID
  • PingID
  • Okta

For SSO authentication, Microsoft Authenticator and Custom Chrome Tabs are supported to act as brokers.

See SSO Requirements.

Note: SSO Language Synchronization: Although Identity Guardian supports full localization, the SSO login interface is hosted externally and operates independently of the application. To ensure the SSO page correctly displays a newly applied device language, reloading the page or restarting the sign-in prompt may be required.

Shared Devices (SD)

In environments where a single device is shared among multiple users, Identity Guardian ensures secure and personalized access tailored to each user's organizational role. To access a shared device, users must first complete a one-time enrollment with Identity Guardian, which can involve capturing the user's facial vectors for facial recognition. Shared devices can support an unlimited number of registered users, offering both flexibility and scalability to organizations.

Administrators configure enrollment settings through Managed Configurations, including:

  • Specifying the required number of facial images for facial biometrics enrollment (if enabled by the administrator).
  • Choosing one of the following:
    • Set barcode or NFC card for user data storage during enrollment. With NFC cards, users can authenticate without requiring additional factors, such as facial scans or passcodes and unlock the device with the simple tap of their NFC card. For more information, see NFC Card. Both rely on the zCreator app.
    • Configure users to authenticate directly against the Identity Provider (Okta, Ping, Microsoft) or Cloud Passcode followed by MPIN entry (from Guardian Safe).

Secure Encryption During Enrollment:

During the enrollment process, sensitive user data, such as biometric facial images and passcodes, is encrypted using an enrollment key. This key is an encrypted public key derived from the organization’s certificate and configured via Identity Guardian Managed Configuration. For guidance on generating an enrollment key, see Enrollment Configuration. It is essential to ensure that the device used for enrollment is provisioned with the correct Enrollment Configuration.

Enrollment Methods:

Identity Guardian offers three distinct enrollment methods for shared devices:

  • Standard Enrollment - This method separates the enrollment and authentication processes across two different devices. It is ideal for scenarios where enrollment is centrally managed, while authentication is distributed.
    • Users enroll on a dedicated device configured with an Enrollment profile deployed by their administrator.
    • After completing enrollment, authentication is performed on a separate shared device configured with the Authentication profile, also deployed by the administrator. Authentication methods such as Single Sign-On (SSO) or user barcodes are used.
  • Self-Enrollment - This method combines both enrollment and authentication on the same shared device. The device is configured with a unified Authentication profile that incorporates enrollment settings defined by the administrator. Users complete enrollment and authenticate directly on the same shared device. This streamlined approach is best suited for environments where users independently manage their enrollment and authentication on shared devices.

For these enrollment methods, there are three main types of secure enrollment mechanisms:

  • Barcode Enrollment: User data is securely encrypted into a unique barcode, which can be shared and printed using the zCreator app. For temporary user profiles, organizations can configure barcodes with expiration dates and times. To further enhance security, organizations may implement facial biometrics as an authentication method. Key differences between enrollment methods:
    • Standard Enrollment - Users can either immediately print the barcode or save it. When the barcode is saved, it is stored in the /enterprise/usr/Profiles folder. After saving, the barcode must be printed or shared within 24 hours, as is automatically deleted afterward to prevent retention of personal information on the device or in the cloud.
    • Self-Enrollment - The user must manually save or print the barcode.
  • NFC Enrollment: Utilizes NFC cards for both user enrollment and authentication. During enrollment, facial biometric vectors and passcodes securely written to the NFC card using the zCreator app. To unlock a device, the user simplify taps the NFC card, followed by a facial scan or passcode entry.
    • Standard Enrollment - Users either immediately write to the NFC card or save the NFC data. When the NFC data is saved, it is accessible through zCreator within 24 hours. Users must use zCreator to write to their NFC card within this time frame, after the data is automatically deleted to prevent retention of personal information on the device or in the cloud.
    • Self-Enrollment - The user must manually save the NFC data or write it to the card.
  • Guardian Safe with MPIN - Secures credentials and personalized settings on Shared Devices using a Master Personal Identification Number (MPIN), enabling profile access across multiple sessions and devices without replacing administrator-configured authentication factors.

Authentication Process:

Barcode or NFC user authentication on shared devices requires an Authentication Key, an encrypted private key derived from the organization’s certificate, which is configured through Identity Guardian's Managed Configuration. To support seamless cryptographic key rotation, an optional Alternate Authentication Key is also configurable. This provides a migration period where both the primary and alternate keys are active, ensuring zero downtime for end-users. For details on key generation, see Shared Device Authentication. The target device must be provisioned with the proper Authentication configuration.

When users scan their enrollment barcode or NFC card, the system decrypts the stored data using either the Authentication Key or Alternate Authentication Key.

Security Warning: The data cannot be decrypted or reverse-engineered on any device without the corresponding authentication key. It is essential that organizations maintain the security and confidentiality of the authentication key to ensure protection of user data.

IMPORTANT: Security Warning Administrators MUST provision specific enrollment and authentication keys on the respective devices used for enrollment and authentication. Failure to do so results in Identity Guardian using default keys, which allows any device with those keys to decrypt the barcode, compromising security.

The zCreator app, a companion to Identity Guardian, simplifies the creation, printing, and sharing of secure user barcodes. Supporting both Standard and Self-Enrollment workflows, zCreator offers features such as barcode preview, resizing, and direct printing for efficient and readable barcode generation. Barcodes can also be easily shared via Gmail or Bluetooth for added flexibility.

Key features:

  • Streamlined Printing Options: Print barcodes directly to supported Zebra and Canon printers via WiFi, Bluetooth, and Ethernet, with:
    • Fixed barcode sizes (3 cm, 4 cm, 5 cm, 6 cm) for consistent printing.

    • Direct printing to supported Zebra and Canon printers for faster workflows.

Secure Setup for Faster Logins

Identity Guardian can simplify Single Sign-On (SSO) logins by prompting users for SSO authentication only once, post device enrollment. For frequent situations like device lock, it offers efficient options like biometric or pin-based access, eliminating the need for repeated SSO logins. It maintains the original SSO session's integrity, ensuring exclusive user access and simultaneous logout from all apps, creating a secure and streamlined login process.

Play Store Updates

To prevent automatic updates from interrupting provisioning and to maintain better version control, select Zebra value-add applications (including Identity Guardian) have Google Play updates disabled by default in the operating system. This change replaces the previous default-enabled state and takes effect starting with the April 2026 LifeGuard releases for Android 14 and Android 15. For supported platforms and devices, see the Zebra Support Portal. While updates are disabled by default, administrators retain full control over application management.

Notes:

  • This change also restricts standard update methods, including manual installation, manual updates via the Google Play Store, and Android Debug Bridge (ADB).
  • This change is not applicable for Android 11 and Android 13, as Play Store updates are enabled by default on these versions.

Administrator Controls: Modify the default setting at any time using MX App Manager with the AllowApplicationUpgrade or DisallowApplicationUpgrade option with one of the following methods:

  • Configuration via MX App Manager: Use this method to submit the XML through the EMM platform to enable/disable automatic updates for Google Play:

    • Enable Automatic Updates: Use the AllowApplicationUpgrade option. Download the Enable_AutoUpgrade_IG.xml.
    • Disable Automatic Updates: Use the DisallowApplicationUpgrade option. Download the Disable_AutoUpgrade_IG.xml.

  • Configuration via Zebra OEMConfig: If using Zebra OEMConfig with the EMM system, follow these steps:

    1. In the EMM system, create a new setting profile using Zebra OEMConfig.

    2. Find the System Configuration section.

    3. Look for the Pass-Through Command field and copy/paste this code to enable automatic updates:

    To disable automatic updates, use:

    <wap-provisioningdoc>
<characteristic version="10.3" type="AppMgr">
<parm name="Action" value="DisallowApplicationUpgrade"/>
<parm name="Package" value="com.zebra.mdna.els"/>
</characteristic>
</wap-provisioningdoc>
